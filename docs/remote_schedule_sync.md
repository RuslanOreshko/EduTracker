# Документація: синхронізація розкладу через SSH

## Призначення

Підсистема синхронізації потрібна для того, щоб застосунок працював із локальною копією SQLite-бази розкладу, але при цьому міг періодично оновлювати її з віддаленого джерела.

У поточній реалізації джерело оновлення завантажується через SSH/SFTP, а локальна копія зберігається в каталозі `data/`.

## Ключові файли

- `src/edutracker/infrastructure/remote/ssh_file_fetcher.py` - завантажує файл з віддаленого сервера через Paramiko.
- `src/edutracker/application/services/schedule_sync_service.py` - координує перевірку актуальності, тимчасовий файл і ротацію кешу.
- `src/edutracker/infrastructure/remote/sqlite_file_validator.py` - валідує, що файл є коректною SQLite-базою і містить потрібну таблицю.
- `src/edutracker/core/config.py` - описує конфігурацію шляхів, SSH-доступу й політики синхронізації.
- `src/edutracker/main.py` - запускає синхронізацію на старті застосунку, якщо вона увімкнена.

## Як це працює зараз

1. На старті застосунку `startup_sync_schedule()` перевіряє `SCHEDULE_SYNC_ENABLED`.
2. Якщо синхронізація ввімкнена, створюється `ScheduleSyncService`.
3. `ensure_fresh_copy()` вирішує, чи потрібне оновлення:
   - якщо локального кешу ще немає, синхронізація запускається одразу;
   - якщо кеш є, порівнюється його `mtime` з `SCHEDULE_SYNC_INTERVAL_HOURS`.
4. Якщо синхронізація потрібна, `sync_now()`:
   - видаляє попередній `.tmp`, якщо він залишився;
   - завантажує віддалений файл у `SCHEDULE_LOCAL_TMP_PATH`;
   - переносить старий кеш у `SCHEDULE_LOCAL_PREV_PATH`;
   - перейменовує `.tmp` у `SCHEDULE_LOCAL_CACHE_PATH`.

## Важливий нюанс поточної реалізації

`SQLiteFileValidator` уже існує і передається в `ScheduleSyncService`, але фактично не використовується перед ротацією файлів. Тобто сервіс завантажує файл і відразу робить його активним кешем без перевірки структури БД.

## Конфігурація

Найважливіші змінні з `Settings`:

| Змінна | Призначення |
| --- | --- |
| `SCHEDULE_SYNC_ENABLED` | Вмикає стартову синхронізацію та використання локального кешу розкладу |
| `SCHEDULE_SYNC_INTERVAL_HOURS` | Максимальний вік локального кешу до повторного оновлення |
| `SCHEDULE_REMOTE_DB_PATH` | Шлях до файлу на віддаленому сервері |
| `SCHEDULE_LOCAL_CACHE_PATH` | Основна локальна копія, з якою працює застосунок |
| `SCHEDULE_LOCAL_PREV_PATH` | Попередня версія кешу для простого rollback-сценарію |
| `SCHEDULE_LOCAL_TMP_PATH` | Тимчасовий файл під час завантаження |
| `SCHEDULE_SSH_HOST` | SSH-хост |
| `SCHEDULE_SSH_PORT` | SSH-порт |
| `SCHEDULE_SSH_USER` | SSH-користувач |
| `SCHEDULE_SSH_PASSWORD` | Пароль для SSH, якщо не використовується ключ |
| `SCHEDULE_SSH_KEY_PATH` | Шлях до приватного SSH-ключа |

## Реальна схема залежностей

- API та репозиторії читають шлях до активної БД через `settings.ACTIVE_SCHEDULE_DB_PATH`.
- Якщо `SCHEDULE_SYNC_ENABLED=False`, застосунок читає основну БД з `DB_PATH`.
- Якщо `SCHEDULE_SYNC_ENABLED=True`, застосунок читає кеш із `SCHEDULE_LOCAL_CACHE_PATH`.

Це означає, що збій у синхронізації напряму впливає на те, яку базу читає продакшн-код.

## Недоліки поточної реалізації

### 1. Небезпечна політика host keys

У `SshFileFetcher` використовується `paramiko.AutoAddPolicy()`. Це автоматично довіряє новому SSH-host key без перевірки. Для тестового середовища це зручно, але для staging/production це ризик MITM-атаки.

### 2. Валідація БД не вбудована в основний happy path

Хоча `SQLiteFileValidator` існує, `ScheduleSyncService.sync_now()` не викликає `self._validator.validate(self._tmp_path)` перед ротацією. У результаті пошкоджений або не той файл може стати активною базою.

### 3. Немає rollback при невалідному завантаженні

Старий файл переноситься в `.prev`, але новий файл не перевіряється до активації. Якщо новий кеш пошкоджений, сервіс уже переключився на нього.

### 4. Обмежена підтримка типів SSH-ключів

`_connect()` читає тільки `paramiko.RSAKey.from_private_key_file(...)`. Якщо середовище використовує `Ed25519`, `ECDSA` або інший формат, підключення зламається.

### 5. Немає доменної обробки помилок

Зараз помилки Paramiko пробиваються наверх майже як є. Це ускладнює:

- зрозумілий лог для оператора;
- коректне API-повідомлення;
- автоматичний retry/backoff;
- відокремлення конфігураційної помилки від мережевої.

### 6. Відсутнє логування критичних етапів

Немає логів на кроках:

- початок синхронізації;
- спосіб аутентифікації;
- успішне завантаження;
- валідація;
- ротація файлів;
- причина падіння.

Для продакшн-підтримки це слабке місце.

### 7. Тести оформлені як скрипти, а не як автоматичні unit/integration tests

Файли на кшталт:

- `src/edutracker/infrastructure/remote/test_ssh_fetcher.py`
- `src/edutracker/infrastructure/remote/test_local_fetcher.py`
- `src/edutracker/infrastructure/remote/test_sqlite_file_validator.py`
- `src/edutracker/application/services/test_schedule_sync_service.py`

виглядають як тести, але по суті це ручні smoke-скрипти з `print(...)`, без `pytest`, без asserts і без моків.

### 8. `SCHEDULE_SOURCE_MODE` поки що не працює як реальний перемикач

У конфігурації є `SCHEDULE_SOURCE_MODE`, але по коду вибір джерела фактично контролюється через `SCHEDULE_SYNC_ENABLED`, а не через окрему стратегію `local/ssh/...`.

### 9. Синхронізація прив'язана до старту застосунку

Якщо SSH недоступний або віддалений файл проблемний, старт застосунку може впасти або зависнути довше, ніж очікується. Для API це погіршує надійність.

## Що краще покращити в першу чергу

### Пріоритет 1: безпечність і коректність

1. Перед ротацією обов'язково викликати `validator.validate(tmp_file)`.
2. Якщо валідація не пройшла, не чіпати поточний кеш.
3. Замінити `AutoAddPolicy()` на контрольований механізм host key verification.
4. Додати підтримку кількох типів приватних ключів.

### Пріоритет 2: експлуатаційна надійність

1. Додати структуровані логи на кожен етап sync-flow.
2. Ввести окремі доменні винятки:
   - `RemoteConnectionError`
   - `RemoteAuthenticationError`
   - `DownloadedFileValidationError`
3. Додати retry з обмеженням кількості спроб.
4. Вирішити, чи помилка синхронізації має блокувати старт API.

### Пріоритет 3: архітектура

1. Виділити інтерфейс fetcher-а, щоб `ScheduleSyncService` залежав не від `SshFileFetcher`, а від абстракції.
2. Реально задіяти `SCHEDULE_SOURCE_MODE` через фабрику джерел.
3. Розвести smoke-скрипти і справжні automated tests.

## Рекомендований цільовий flow

Більш надійний сценарій має виглядати так:

1. Завантажити віддалений файл у `.tmp`.
2. Перевірити, що файл існує, не порожній і є валідною SQLite-базою.
3. Перевірити наявність потрібних таблиць.
4. Лише після цього замінити поточний кеш.
5. Якщо щось пішло не так, залишити старий кеш активним і записати причину в лог.

## Як читати цей код, якщо бракує контексту

Найкращий порядок читання:

1. `src/edutracker/main.py` - побачити, коли синхронізація запускається.
2. `src/edutracker/application/services/schedule_sync_service.py` - зрозуміти оркестрацію процесу.
3. `src/edutracker/infrastructure/remote/ssh_file_fetcher.py` - подивитися, як саме качається файл.
4. `src/edutracker/infrastructure/remote/sqlite_file_validator.py` - зрозуміти, які інваріанти БД вже можна перевіряти.
5. `src/edutracker/core/config.py` - перевірити, які env-змінні реально керують поведінкою.

## Короткий висновок

Поточна реалізація вже має правильний базовий напрямок:

- окремий fetcher;
- окремий сервіс синхронізації;
- окремий валідатор;
- окремі шляхи для `tmp/current/prev`.

Але їй бракує двох речей, критичних для production-рівня: вбудованої валідації перед активацією кешу та безпечної SSH-політики. Саме ці два пункти дадуть найбільший приріст якості.
